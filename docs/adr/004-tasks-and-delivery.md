# ADR 004：任务完成与用户收到结果分别确认

状态：采用。作者：Kenneth。日期：2026-09-07。

## 问题

一个子任务写好了 PDF，并不等于整个任务成功，更不等于群友已经收到文件。
把这些状态合并会造成“显示完成但没附件”，随后销毁沙盒还会丢掉补发机会。

## 决策

- 主控拆分目标、依赖和验收条件；专业子智能体拥有各自的工作上下文，不互相复制完整历史。
- 可独立执行的步骤并行；依赖满足后才领取下游步骤。产物和证据通过明确合同传递。
- 步骤状态、总任务状态、产物状态和投递状态分别保存。部分结果不提前冒充最终成功。
- 长任务以持久记录、租约、检查点和执行代次支持重启后接管。
- 文件交付前登记独立于任务容器的产物快照，核对大小、摘要和目标会话。
- Outbox 负责发送和回执；QQ 回执不明进入待核对状态，不能因为超时就重复发一遍。
- 沙盒生命周期与模型宣称完成解耦。保留、清理策略必须先检查产物和未完成投递。

## 实现位置

`src/plugins/ai_chat/agent/` 定义角色、合同及上下文边界；`subagents.py` 负责现有编排。
`delivery.py`、`onebot_delivery.py`、`sandbox.py` 管理投递与工作区。
`src/cluster_control/` 和 `src/cluster_worker/` 管理远程固定任务的合同、资源租约及回执。

## 取舍

不把每个普通问答都拆成多智能体：拆分和汇总有实际延迟及 token 成本。
不以容器退出码作为用户级验收：文件可能存在但不可读，或根本没发出。
不承诺 QQ 的端到端 exactly-once：上游回执不足时必须保留不确定性并对账。
代价是状态更多，控制台需要清晰展示执行、交付和异常恢复的不同阶段。

## 回归检查

覆盖工作成功但发送失败、收到回执前重启、依赖任务失败、租约过期后旧 Worker 继续回报、
取消与完成同时发生。验收必须确认目标群实际收到文件，且失败后仍能找到产物。
