# Kennethbot Subagent V2：独立上下文与任务感知模型路由整合方案

调研日期：2026-09-05。项目基线：`ab94544`，版本 `0.10.2`。

本文包含整体设计和下述本地实施记录，不代表全部功能已经实现或部署。参考官方开源仓库及官方文档；SDK 暴露的能力不等于 Claude、ChatGPT 等产品的全部内部实现。上游 `main` 分支可能领先稳定发布版，实施时必须固定版本并验证接口。

### 本地实施记录（2026-09-05）

本轮完成前半部分的基础执行链，不修改生产主机或数据库拓扑：

- `agent/execution.py`：强制第一次主模型调用返回 direct/delegate/workflow、任务类型、目标、交付物、约束、验收描述和依赖计划。普通直接回答包含在这一次结果中；简单工具查询继续原 ReAct，不另外创建团队。原正则仅保留为轻量模型选型提示，不再决定是否允许分工。
- 宿主拒绝“project 却 direct”、缺失交付标准、重复 ID、未知角色、越界依赖和循环；无效合同最多修正一次，仍失败就停止，不偷偷改成主控独自做。有效 workflow 计划直接复用，不再调用 planner。
- 保留用户原始请求和宿主绑定的群、会话、用户，模型只提供解释和拆分；不能用模型改写后的短目标覆盖原要求。自动入口遵守管理员工具开关；项目写入和执行绑定专业子任务。
- `agent/sessions.py` 和 Alembic `0017_subagent_sessions`：一个任务步骤一份带版本号的子会话，保存实际模型可见的 user/assistant/tool 记录；同角色不同步骤不共用历史。重试及已有 interrupted 任务恢复沿用自己的记录；版本冲突停止写入。不会持久化宿主 system 提示词。
- 上游最终结果仍完整保存在运行记录中；上下文只放有效 JSON 索引，子任务通过 `read_agent_result` 分页读取自身已交接的直接上游结果，不再截断 JSON。工具原始大型文件继续使用现有产物存储。
- `agent/model_routing.py`：代码、主控、分析、运维优先 Terra；检索、文档、媒体优先 Luna，并保留 Qwen 等配置内备选。角色显式覆盖优先。自动候选和降级都排除 Sol 及底层未确认的 `codex-auto-review`，除非管理员显式配置；不改变 Qwen 思考或熔断设置。这里使用已配置能力，不宣称全部渠道已经实测。
- 每个子任务记录期望、选择和实际路由、代理响应型号标识、Token、有效轮次与超时。代理响应型号不是底层模型的独立鉴定。角色轮次与全局预算取最小值；默认全局由 6 提高到 20，显式配置仍优先。
- 结果状态、结构合同校验与投递状态分开；缺少 status/summary 或仍有 unresolved 不算完整成功。新合同声明需要投递却没有产物时不能完成。`acknowledged` 表示发送工具收到成功回执，不承诺 QQ 客户端必然已显示。

后半部分已在 0.11.0 代码中接入：自然语言 revise 与版本化追加修改、独立验收与有限修复、任务及角色的 auto/preferred/locked 模型编辑、后台租约接管与写入 fencing、未知上传对账、独立容器和只读产物交接，以及实时任务控制面。详见 [运维说明](subagent-v2-operations.md)。历史缺少派发身份的任务仍手动恢复；无验收环境明确标为未验收，不假装通过。

新入口开关：`AI_SUBAGENT_ENTRY_ENABLED=true`。关闭后保留 `/task` 和模型工具委派，不删除任务和子会话。迁移需要在部署时执行 `alembic upgrade head` 到 `0018_subagent_controls`。上线状态以实际部署记录为准，本文不替代运行检查。

关键回归覆盖入口合同、直接回答一次调用、计划复用、同角色真实并行、独立会话恢复、范围拒绝、投递缺失及非 Sol 降级。`tests/fixtures/subagent_entry_cases.json` 保存 8 个成对语义案例；`python tools/evaluate_subagent_entry.py` 仅检查案例，不调用模型。上线前可显式执行 `python tools/evaluate_subagent_entry.py --live --profile gpt-5.6-terra --limit 8` 做小样本验证，只判断入口、不会执行任务工具。本轮未消耗模型额度跑语义评测，不将模拟回归结果当成实际入口命中率。

本文合并上游编排设计、Kennethbot 现有实现和 2026-09-05 的运行中模型目录检查。最终目标是：主控自然接收请求，按需派出使用合适模型的专家；专家各自保留工作记录，完成后经过验收和可靠投递，而不是只显示几块正在运行的方框。

## 1. 结论

保留 Kennethbot 的 NoneBot、模型网关、PostgreSQL、工具权限、沙盒和 React 控制台。在现有协调器上逐步补齐，不同时引入六套框架。

推荐的组合是：

- OpenAI 的主控统一对话模式。
- Claude 的独立、可继续执行的子会话。
- Google 的显式依赖和结构化工作流。
- Microsoft 的完整检查点及恢复兼容性检查。
- Deep Agents 的上下文隔离和受控结果交接。
- AgentScope 生态的可见协作、运行环境和凭据管理分离。

以上是本文的整合判断，不是某一家已经完整实现的同一套架构。Subagent 的价值是并行、专业分工和减少上下文干扰，不保证增加数量就提高答案质量。

## 2. 各家怎么做

### OpenAI：主控调用专家，或者把对话交给专家

Agents SDK 区分两种模式：`agents as tools` 让主控调用专家后继续组织最终答案；`handoffs` 则把当前轮的主动对话权交给专家。官方同时支持模型决定分工和代码决定流程。

Kennethbot 应主要采用第一种：搜索、代码、文件等子任务交给专家，Kenneth 继续理解群聊、维持人设、统一回复。工具授权仍由宿主执行，不能认为选了某个编排模式就自动获得完整安全边界。

来源：[官方多 Agent 设计说明](https://github.com/openai/openai-agents-python/blob/main/docs/multi_agent.md)。

### Anthropic：每个子 Agent 有自己的工作对话

Claude Agent SDK 的子 Agent 默认具有独立上下文，可以配置说明、提示词、工具和模型；主控通常收到最终结果，而不是全部中间工具记录。官方文档还说明了利用会话及 Agent 标识继续原有子会话的方式。

Kennethbot 值得借鉴的是“继续同一个任务”的语义：第二次修改 PDF 时，让文件 Agent 在自己已读的资料和已做的操作上继续，而不是重新开一张白纸。SDK 示例及文档不等于公开了 Claude 的全部调度源码。

来源：[官方角色配置示例](https://github.com/anthropics/claude-agent-sdk-python/blob/main/examples/agents.py)、[官方子 Agent 文档](https://code.claude.com/docs/en/agent-sdk/subagents)。

### Google：依赖关系写清楚，数据按结构传递

Google ADK 的并行实现为不同分支标记执行上下文并汇合事件；官方仓库的 Workflow 指南进一步描述了节点、边、结构化输入输出、汇合节点、动态调度和重试。分支标识本身不等于租户数据权限隔离。

Kennethbot 应保留已有的“某个步骤依赖满足就立即启动”调度，借鉴显式结果结构和事件化状态更新。不要退回“这一批全部结束才开始下一批”。具体 Workflow 接口以采用的发布版为准。

来源：[并行 Agent 源码](https://github.com/google/adk-python/blob/main/src/google/adk/agents/parallel_agent.py)、[官方 Workflow 指南](https://github.com/google/agents-cli/blob/main/skills/google-agents-cli-adk-code/references/adk-workflows.md)。

### Microsoft：恢复的不只是 finished/running 标签

Agent Framework 的检查点包括工作流身份、图结构签名、前一检查点、已提交状态、消息、待处理请求和格式版本。恢复时需要知道执行到了哪里，也需要确认新版程序还能读懂旧任务。

Kennethbot 应借鉴完整状态和版本校验，用现有 PostgreSQL 实现。保存检查点与“进程重启后自动继续”是两件事，后者还需要执行进程接管任务；检查点也不能保证外部发送恰好执行一次。

来源：[检查点源码](https://github.com/microsoft/agent-framework/blob/main/python/packages/core/agent_framework/_workflows/_checkpoint.py)、[工作流示例目录](https://github.com/microsoft/agent-framework/blob/main/python/samples/03-workflows/README.md)。

### LangChain Deep Agents：不要把专家的所有工作塞回主控

Deep Agents 的子 Agent 中间件默认以委派说明作为子 Agent 的起始消息，明确排除部分父状态，例如原始消息和待办；结果返回也有状态过滤。源码另有实验性的 fork 模式，不能把它和默认隔离模式混为一谈。

Kennethbot 应借鉴受控交接：默认传任务、必要证据和上游摘要，不广播所有 Agent 的完整对话。完整资料保存在宿主，需要时按引用读取，而不是将巨大 JSON 硬截断后拼给模型。

来源：[Subagent 中间件源码](https://github.com/langchain-ai/deepagents/blob/main/libs/deepagents/deepagents/middleware/subagents.py)。

### AgentScope 生态：协作过程也应当是可管理的产品

AgentTeams 是比单个 Agent SDK 更高一层的协作系统：Manager 组织 Worker，通过即时通信呈现协作；网关管理模型和工具访问，存储保存工作资料，控制器管理运行环境。Worker 可以具有不同角色和运行配置。

Kennethbot 应借鉴职责分离及可见进度，但无需搬入它整套 Matrix、网关和容器控制平台。已有 QQ、模型网关和控制台可以承接这些职责。不要把 AgentTeams 的能力直接当成所有 AgentScope 版本的能力。

来源：[AgentTeams 官方架构概览](https://github.com/agentscope-ai/AgentTeams/blob/main/docs/overview.md)。

## 3. Kennethbot 已有什么，真正差在哪里

已经存在的能力应保留：固定专家角色、自动委派入口、依赖图、并行执行、角色工具白名单、独立上下文快照、结构化结果、任务事件、检查点、有限修复，以及控制台任务图。

本地代码确认的主要差距：

| 位置 | 现在的行为 | V2 应补齐 |
| --- | --- | --- |
| `AgentResult.from_payload` | 缺少合法状态且没有 unresolved 时，会默认为 success；空对象也可能被解释为成功 | 缺失必需字段作为无效结果；执行结束和验收通过分开 |
| `ContextPacket.for_agent` | 上游 JSON 截取前 3600 个字符，再参与总字符预算 | 保留结构完整的摘要、证据和产物引用；完整内容可按需读取 |
| `_run_step` | 保存初始上下文，但模型调用传入空历史；事件记录也有截断 | 保存子会话消息和完整工具结果引用，支持真正的继续执行 |
| 角色配置与运行入口 | 声明了模型策略、轮次等字段，但 worker 仍使用协调器统一工具轮次 | 建立单一策略解析入口，让配置、实际执行和控制台一致 |
| `recover_interrupted` | 重启后标记 interrupted，已有手动恢复路径 | 安全步骤可由后台执行进程自动接管；不确定副作用先对账 |
| `_execute_workflow` | 先尝试投递文件，再进入主控 verifying/总结阶段 | 产物检查通过后进入投递队列，最后根据实际回执报告结果 |

这里不是说现有系统完全没有隔离、重试、检查点或产物处理。问题是它们还没有组成一致的任务完成协议。单独委派入口已使用角色超时，不能笼统说所有角色限制都没生效。

代码依据：[结果与上下文合同](https://github.com/zty20040403/chat-bot/blob/ab94544/src/plugins/ai_chat/agent/contracts.py#L174)、[结果状态处理](https://github.com/zty20040403/chat-bot/blob/ab94544/src/plugins/ai_chat/agent/contracts.py#L315)、[worker 执行](https://github.com/zty20040403/chat-bot/blob/ab94544/src/plugins/ai_chat/subagents.py#L2132)、[工作流和发送顺序](https://github.com/zty20040403/chat-bot/blob/ab94544/src/plugins/ai_chat/subagents.py#L1692)、[重启处理](https://github.com/zty20040403/chat-bot/blob/ab94544/src/plugins/ai_chat/subagents.py#L876)。

### 3.1 模型目录检查快照

以下来自 2026-09-05 对 h610 运行中管理 API 的只读检查，不是永久健康结论，也没有逐个模型额外发送生成测试：

| 分类 | 配置 | V2 自动选型策略 |
| --- | --- | --- |
| 有近期成功记录 | `qwen-local`、`gpt-5.6-terra` | 作为候选起点；仍需按具体任务验证工具、输出格式等能力 |
| 有成功记录但型号不透明 | `codex-auto-review` | 确认真实映射和能力前，不纳入按专长自动选择的候选池 |
| 最近返回计费错误 | `deepseek`、`deepseek-pro` | 按已有健康策略暂时避开；计费恢复并验证后再纳入 |
| 已配置、此次进程没有请求记录 | `gpt-5.6-sol`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-5.4`、`gpt-5.4-mini`、`gpt-5.3-codex-spark` | 小规模验证实际代理渠道后再开放自动选择 |

必须区分“出现在目录中”“管理员允许”“渠道可调用”“当前任务能力合格”。一次文字响应成功不能证明支持视觉、工具调用或较长上下文。

能力目录需要先校正：千问的公开模型支持视觉，但部署配置为 `vision=false`，未验证服务端之前仍按不能直接接收图片处理。Spark 在当前配置里被统一设为 `vision=true`，而官方标为纯文本，应从视觉候选排除。5.4 和 5.4 Mini 的 ChatGPT 登录 Codex 渠道已退役，直接 API 不受这一退役影响；使用代理时必须确认实际渠道。来源：[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen3.8-27B)、[OpenAI 官方模型与渠道说明](https://learn.chatgpt.com/docs/models)。

## 4. 整合后的结构

```text
QQ / 后续其他平台
        |
Kenneth 主控：理解对话、自动决定是否委派、统一答复
        |
任务合同：目标、约束、产物、验收标准、授权范围
        |
任务感知模型路由：能力过滤、角色偏好、权限、实际渠道
        |
持久协调器：依赖调度、子会话、任务接管、取消
        |
        +-- 搜索子会话：独立对话、工具、工作记录
        +-- 代码子会话：独立对话、工具、工作目录
        +-- 文件子会话：独立对话、工具、产物引用
        +-- 媒体 / 分析 / 运维：按任务需要启动
        |
宿主验收：结构、证据、文件和执行结果
        |
持久投递队列：发送、记录回执、处理状态不明
        |
Kenneth 最终答复

各阶段的真实事件 -> PostgreSQL -> SSE 控制台 / QQ 进度
```

“宿主”就是你自己的 Python 程序。模型负责建议做什么；Python 程序负责权限、保存状态、实际执行和判断是否允许交付。

### 4.1 自动用，但不是每句话都开团队

这是第一优先级的行为修复。2026-09-05 在日志中找到“精心写个谷粒商城”，对当前纯路由函数的本地复现返回 `delegate=false`；“前端后端分工并行实现，最后测试打包”也未触发，而“完整项目”可以触发。它确认了关键词前置路由的漏判，不构成对该轮所有模型行为的完整 Trace 分析。

取消“关键词没命中，因此当作普通聊天”的默认结论。保留 direct、delegate、workflow 三种执行方式，但将它们作为主控必须明确给出的执行决定：

| 模式 | 适合的请求 | 例子 |
| --- | --- | --- |
| direct | 自然对话、解释、短代码示例，或少量只读查询 | “谷粒商城是什么”“解释这段代码” |
| delegate | 一个有明确交付目标的专业任务 | 解析一份文件、修复一个局部错误 |
| workflow | 存在不同交付部分、前后依赖或集成验收 | “写个谷粒商城”“比较产品并做成 PDF” |

“同一个领域”也可以拆分。例如前端和后端都属于 coder，但有两个独立职责和上下文。不能再要求命中至少几个专业领域或必须写出“完整项目”才接受分工。

#### 判断放在主控本来就要进行的调用里

不额外给每条群消息增加一个模型分类器，也不重新启用主动插话。仅当机器人原本就应该处理这轮请求时，让第一轮主控读取现有授权上下文，并输出结构化执行决定，或调用相应的受约束工具。

建议的执行决定至少包含：`mode`、`objective`、`task_type`、`deliverables`、`constraints`、`context_refs`、`short_reason`，委派时再包含专家步骤与依赖。`short_reason` 是可公开的短说明，不要求输出隐藏推理过程。

普通直接回复的内容可以随决定一起返回，宿主解析后发送，无需为了分工判断再调用一次模型。需要读工具时走现有主控工具循环；需要专家时进入协调器。各 provider 使用其实际支持的工具或结构化输出协议适配，不能直接向 QQ 显示内部 JSON。直接答复首轮需要结构验证，流式展示要避免泄露协议字段，并测量这一变化对首字延迟的影响。

初始规划里已有合法步骤时，协调器直接校验并持久化执行，不再固定增加一轮重复的“规划模型”。复杂任务确实需要澄清范围或修订计划时再调用主控。

关键词只适合显式命令解析和轻量提示，不再拥有否决语义分工的权力。`/task` 保留为用户可选的强制任务入口，不成为自然语言请求的使用门槛。

#### 不只靠提示词，也有执行边界

对创建项目、修改多个文件、构建和交付等持久工作，沙盒执行必须绑定任务合同与 task/step 身份。主控不再直接暴露可用于无记录完成整个项目的写入入口；需要实际执行时通过有记录的 worker 获取相应工具。一个简单脚本可以只委派一个专家，不必虚构多 Agent 团队。

宿主检查模式与结构是否一致：已经声明多个独立交付部分却选择 direct、依赖无效、产物缺少作者或权限不匹配时，要求修正决定。无效 JSON 不默认变成 direct；执行失败也不静默回到主控手工干完整项目。

这不能数学上保证模型永远正确理解每个自然语言请求。需要用成对案例检验：解释商城概念不启动工作流，实际要求开发商城进入项目任务；仅修改一个按钮也不机械开多人团队。不要用新增“谷粒商城”专用关键词替代这项修复。

#### 范围、消息和项目连续性

执行决定必须基于当前消息和已选择的话题上下文，不能只看最后一句文字。已有授权项目里说“继续”“改成 Java”“再加购物车”，应形成同一任务的新修订，而不是忘掉要求重新分类为独立闲聊。

“做谷粒商城”需要界定本轮交付范围。可以根据已有上下文给出阶段计划和合理默认，但不能悄悄把完整微服务项目缩水成一个演示页后声称全部完成。费用、外部部署和关键范围不清楚时只确认必要事项；不要因为用户没列技术术语就不进入任务模式。

### 4.2 每个职责有独立上下文，还要能延续

区分三个对象：

| 对象 | 通俗含义 | 生命周期 |
| --- | --- | --- |
| AgentDefinition | 某种专家的岗位说明、模型策略和工具权限 | 可被很多任务复用 |
| AgentSession | 这位专家处理这件事的工作记录 | 在授权的同一任务中可以继续 |
| AgentRun | 某次实际执行或重试 | 一次开始到一次结束 |

同样是 researcher，不代表所有群共享一份 researcher 聊天记录。同一个任务里的三个 researcher 也拥有三个不同的子会话。

默认新子会话只收到：目标、限制、必要的群聊证据、获准读取的记忆、相关资料、上游结果引用。主控的连续群聊时间线保持原样，不为子 Agent 再次重写你的全局上下文逻辑。

用户说“这个报告补一页”时，可以继续同一任务的 document 子会话，带上新要求和之前产物的版本；不能把所有旧消息复制给新的任意角色。

持久化对话消息、工具调用、结果引用和必要的续跑状态；不要求保存或向管理员展示模型隐藏推理。不同模型的会话格式通过当前模型网关适配，不假设 provider 的会话 ID 可以跨模型复用。

每次读取历史、证据或产物都检查 scope 和资源权限。群公开任务可以在群权限内共享，但 A 的私有记忆不能因为 B 接着问而泄露。会话恢复权限也必须重新检查。

### 4.3 任务和结果都要有明确合同

每个任务需要：目标、必须完成的子目标、输入引用、依赖、交付物类型、验收规则、截止时间、发起者和授权范围。

每个结果至少区分：

- `execution_status`：程序执行成功、失败、取消或中断。
- `completion_status`：业务目标完成、部分完成或未完成。
- `validation_status`：未验收、通过或不通过。
- `summary`、`evidence_refs`、`artifact_refs`、`unresolved`。
- `expected_model`、`actual_model`、用量和耗时。

这些字段是建议扩展现有合同，不是要求另存一套重复的事实。使用类型化验证，不能让模型返回一个空对象就显示成功。

上游给下游的是完整、较短的结构化摘要和引用列表。完整工具输出和资料另存；按章节、页码或区间读取，避免把 JSON 截成半截。预算按模型窗口和任务复杂度分配，优先保留目标、必需证据和工具输出预留空间。

### 4.4 真实并行，也允许有限改计划

保留当前 ready-queue 调度：只等自己的依赖，不等无关的慢 Agent。

允许主控提出增加步骤、重做某一步或取消冗余步骤，但宿主必须校验：依赖无环、权限不增加、资源允许、已完成结果不被悄悄覆盖。子 Agent 缺资料时先报告需要什么，由主控决定补检索或改计划；第一阶段不开放无限递归创建。

明确必需依赖和可选依赖。可选来源失败不应让整份报告消失；必需数据缺失则不能伪装成完整结果。限制重复调查相同问题，记录证据来源及引用关系。

增加跨任务的资源调度，而不只是每个任务内部并发：按模型容量、沙盒资源及群公平性排队，给普通聊天保留处理空间。阈值应根据实际机器和服务承载配置，不在本方案里凭空固定。

并行写代码时，使用独立工作目录或 worktree，必要时独立容器；目录分离只解决写入冲突，不等于安全隔离。上游产物以只读版本交接，集成步骤合并改动并验证，不让几个 Agent 同时覆盖同一文件。

### 4.5 先验收，再发送

用你常见的 PDF 任务举例：

1. 检查产物确实存在、非空、类型正确。
2. 检查 PDF 能打开、页数合理、文本或图表内容满足任务要求。
3. 检查所需中文字体覆盖和嵌入；必要时抽页渲染检查。仅能提取文字不代表显示一定正确。
4. 检查引用和来源；需要判断表达质量时才增加模型复核。
5. 通过后写入投递队列，读取真实发送结果。

验收器不是每轮都调用一个昂贵的“评审 Agent”。确定的条件由代码检查，只有主观质量或证据冲突需要模型参与。搜索任务也不能只检查“有链接”，必须把结论与支持它的来源关联起来。

需要发到 QQ 的工具由宿主统一执行。子 Agent 可以提交产物和发送请求，但不直接绕过验收发布。模型说“已发送”不能替代回执。

### 4.6 失败后修局部，不从头重来

| 情况 | 推荐处理 |
| --- | --- |
| 短暂网络错误、限流 | 根据错误类型有限重试，保留已有结果 |
| 模型不支持工具或视觉 | 根据能力要求换实际可用模型，记录降级原因 |
| 缺关键资料 | 定向补资料或重开对应子会话，不重跑全部步骤 |
| 产物验收失败 | 把具体失败检查交回产物作者修复 |
| 达到预算或期限 | 保存可用的部分结果，并明确缺失内容 |
| 操作可能已生效、回执丢失 | 查询或对账；不能盲目再发送、再扣费或再删除 |
| 进程重启 | 新执行进程接管到期任务；从可安全恢复的位置继续 |
| 用户取消 | 停止后续调度，传播取消，记录仍在执行或无法撤回的操作 |

后台接管在 PostgreSQL 上实现领取锁、租约、心跳和执行代号。旧进程失去租约后不能继续提交任务完成状态；外部副作用仍需调用前授权与幂等键，不能只靠数据库锁。

检查点保存计划版本、会话版本、已完成步骤、结果引用、待审批操作和投递状态。恢复时检查定义/数据格式是否兼容，不兼容就等待迁移或管理员处理。

承诺应是“可恢复执行、幂等去重、状态不明可对账”，不是保证 QQ 等外部平台绝对只收到一次。既有 jobs/outbox 能复用就复用，暂时不新增 Redis、Temporal 或 Kubernetes。

### 4.7 模型与权限配置真正生效

不同子 Agent 应当可以使用适合当前任务的不同模型。这不是每个角色永久绑定一个模型，而是“角色默认策略 + 本次任务要求 + 宿主模型路由”。

当前 `_profile_for` 只读取角色固定覆盖，否则继承主模型；下述自动选择仍是待实施设计，不能把已有的 `model_policy` 标签当成已经具备任务感知路由。

#### 选择过程

```text
主控或子 Agent 提出任务要求
    |
过滤：管理员启用 + 当前用户/群允许 + 具备必需能力
    |
选择：明确指定 > 角色偏好 > 已配置的任务适配排序
    |
执行：记录期望模型、实际模型、选择理由和推理设置
    |
必要时请求换模型：重新校验权限和能力，再继续同一子任务
```

任务要求应是结构化字段，例如是否调用工具、是否直接接收图片、输入长度、是否复杂推理，以及偏重质量还是速度。模型可以提出偏好，但不能自己新增 API 地址、获取密钥或宣称某个未验证模型具备能力。

优先级只在符合权限和必需能力的候选中生效。管理员“锁定模型”与“首选模型”需要区分：锁定时不静默换模型；首选时可以按明确授权的链路降级。无合格候选就说明哪项能力不可用，不能为了继续执行把图片交给不支持图片的模型。

#### 按工作挑选，而不是按角色名字猜测

| 子任务示例 | 选模型时优先考虑 |
| --- | --- |
| 搜索网页、提取几个事实 | 工具调用可靠性、延迟、成本 |
| 排查复杂代码错误、修改多文件项目 | 代码任务实际表现、工具调用、足够的上下文空间 |
| 比较矛盾证据、做统计分析 | 推理任务表现、工具使用和证据核对能力 |
| 直接分析图片或视频抽帧 | 当前输入链路实际需要的视觉能力 |
| 阅读文本 PDF、生成报告 | 长文本处理、内容组织、代码/文件工具能力 |
| 分析扫描版 PDF | 直接视觉或 OCR 工具链；按实际方案选择，不一律要求主模型支持视觉 |
| 只查询服务状态或告警数量 | 可靠地调用工具和解读结果，通常不必使用最昂贵模型 |

这里不预设某个品牌永远擅长某类任务。第一版用管理员配置的能力和任务偏好排序；逐步积累分任务类型的验收结果、延迟和用量，再辅助调整排序。未经验证的模型能力显示为未知，不自动视为支持。

各子 Agent 独立选型，不修改主控或群的默认模型。一个任务里可以同时有三个不同模型工作；复用同一 provider/模型客户端时也不共享不同子会话的消息历史。

#### Kennethbot 的初始任务偏好

下表是候选模型通过渠道及能力验证后的目标分配，不是立即切换生产配置，也不是固定品牌排名。同一个角色可因任务不同采用不同配置。

| 角色 | 常规任务候选 | 复杂任务候选 | 选择依据 |
| --- | --- | --- | --- |
| supervisor 主控 | Terra | Terra；Sol 仅显式指定 | 常规拆分与汇总，或需要深度判断的开放任务 |
| researcher 搜索 | Luna；已验证的千问文本工具链 | Terra | 单纯提取事实，或需要处理来源矛盾、复杂调查 |
| coder 代码 | Terra；小范围文本代码修改可选 Spark | Terra；Sol 仅显式指定 | 代码改动范围、工具步骤和验收难度 |
| document 文件 | Luna / Terra | Terra | 文本提取、制作普通报告，或复杂文档分析与高质量交付 |
| media 媒体 | Luna | Terra | 简介标签，或细节、图表、多图关系分析 |
| analyst 分析 | Terra | Terra；恢复并验证后的 DeepSeek Pro | 统计汇总，或多步骤推理、证据冲突 |
| operator 运维 | Terra | Terra | 状态查询，或跨服务故障分析；权限不随模型能力扩大 |

Terra 的均衡定位、Luna 的高吞吐低成本定位和 Sol 的复杂专业工作定位分别见：[Terra](https://developers.openai.com/api/docs/models/gpt-5.6-terra)、[Luna](https://developers.openai.com/api/docs/models/gpt-5.6-luna)、[Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol)。表中的具体岗位分配是本项目的设计判断，需要任务验收数据验证。

GPT-5.5 保留为经过验证的复杂任务备用候选；5.4/5.4 Mini 按实际渠道决定是否保留，不因目录有名称就自动启用。DeepSeek Flash/Pro 恢复后分别进入常规文本工具任务与复杂分析候选。`codex-auto-review` 未确认底层型号前不参与专长评分。备选均须同时满足权限与任务能力，不能直接遍历全目录随便找一个顶上。

千问保留当前思考与调试设置，不擅自关闭思考来制造低延迟。是否让它承担批量抽取或代码工作，要结合该部署的排队时间和实际验收表现；在同学的机器上运行不意味着可以承诺无限并发或零成本。

推理强度初始策略是：清楚的提取任务优先 low，普通多步任务 medium，复杂代码/分析 high；只有难题或局部验收失败后才考虑 xhigh。这里不是给所有 provider 原样传相同字符串，网关必须映射到各自支持的设置；用户显式锁定的支持项优先。

CLIProxy 的实际额度与上游 API 标价未必一致。第一阶段记录 Token、延迟、失败、限流和验收结果；没有可靠价格数据时显示用量而不是编造人民币成本。

#### 权限与可解释选择

沿用控制台“自己 / 其他群友”两类模型权限及既有群、用户覆盖。最终候选必须同时满足全局启用、发起者有效权限、角色要求和任务能力。主控或子 Agent 不能通过改名、直接填模型 ID、换 provider 或请求降级绕开限制。

每次模型请求都记录路由过程，不能只在任务创建时记录一次：

- 期望模型：本次偏好或用户指定的配置。
- 选定模型：经过能力、权限及适用健康策略检查后的配置。
- 实际模型：网关此次真正请求的配置及响应中的模型标识。
- 原因：首选命中、权限过滤、能力不符、健康跳过、调用降级或质量升级。
- 附带：策略版本、推理参数、输入输出 Token、耗时和失败分类。

如果代理不提供可验证的底层型号，明确显示“代理返回标识，底层未确认”，不能把转发时填入的模型名当成独立鉴定结果。原有 `model_profile` 字段保留兼容语义，新字段增量添加，避免旧控制台误读。

#### 换模型的时机

每个子任务开始时选择一次，正常执行过程中保持稳定。明确的能力不匹配、模型调用失败、上下文不足或验收后需要更强推理时，才允许请求重新选择，并记录原因和已经尝试的配置，避免来回切换。

换模型只转移兼容的任务消息、证据、工具结果与产物引用；不直接复用其他 provider 的会话状态。保留已完成动作和副作用记录，不因为换模型就重发文件或重跑整个任务。

沿用已有模型降级、健康状态和管理员调试设置；这一步不额外给已关闭熔断的本地千问偷偷添加新的熔断。任务截止时间和工具安全策略仍照常生效。

控制台按子任务展示角色、任务摘要、自动/首选/锁定模式、候选配置、期望模型、实际模型、选择或降级原因、推理强度、Token 和耗时。当前运行采用策略快照，管理员修改默认影响后续运行，避免执行中途无提示地换配置。

#### 统一执行入口

为所有执行路径统一解析角色策略，包括模型能力、期望模型、实际降级链、推理强度、轮次和超时。不要在注册表里声明 20 轮，实际却无声使用统一的 6 轮。

推理强度按 provider 能力映射，不支持时显示不支持。配置、Agent Trace 和控制台使用同一份解析后的策略。是否使用便宜模型应依据任务表现验证，不能只按角色名字决定。

子 Agent 只能使用批准的工具子集；沙盒不能直接拿宿主机密钥，模型访问经宿主网关。高风险权限由用户授权或审批决定，子 Agent 自己不能通过生成提示词获得新权限。

### 4.8 控制台与 say 用同一条真实事件流

每个执行事件包含 task、session、run、step、时间、序号、状态和简短说明；敏感参数脱敏。数据库提交状态时可靠记录事件，SSE 断线后按游标补齐，并校验访问权限。

控制台方块展示真实状态：排队、调用模型、执行工具、等待输入、验收、修复、投递、完成。显示期望/实际模型、用量、耗时、当前动作；长内容放详情页。箭头表示真实依赖与结果交接，不用动画代替状态。

列表只保留最近五条及简短摘要，点开新详情页查看全部；任务图保留放大入口。实时事件只更新数据实体，不重建下拉框和编辑表单。配置编辑携带资源版本，冲突时提示重新确认；修改和取消、审批等操作都有审计记录。新增模型路由设置接入现有控制 API，不另开无鉴权入口。

QQ 的 say 也读取这些事件，例如“搜索 Agent 找到三个来源，分析 Agent 开始比较”“PDF 字体检查未通过，正在重新生成”。合并同一状态的重复通知，保留开始、关键进展、阻塞和结果，不伪造进度百分比。

### 4.9 数据和代码如何落地

继续以 h610 的现有 PostgreSQL 为任务事实来源，不改变主备和归档拓扑。复用已有任务、运行、检查点、工具审批和投递存储，不另建相同职责的第二套系统。

建议以增量迁移补充下列数据：

| 数据 | 保存什么 | 关键边界 |
| --- | --- | --- |
| 任务 | 目标、必需交付物、验收规则、scope、发起者、策略和计划版本 | 不随模型切换失去原始要求 |
| 子会话 | task/step/role 身份、范围和持久对话消息 | 一个角色的不同任务不共用会话 |
| 运行尝试 | session、attempt、路由过程、用量、开始结束与错误 | 重试有独立记录，不覆盖历史 |
| 证据与产物 | 来源、版本、哈希、访问权限、存储引用、验收结果 | 摘要和真正文件可对应，不能只有失效路径 |
| 执行状态 | 检查点、租约、持有者、执行代号、待审批或待恢复操作 | 重启与多执行进程接管可校验 |
| 事件和投递 | 单调事件序号、发送意图、幂等键、回执与状态不明记录 | 展示、重放检查与真正重新执行分开 |

追加要求形成任务修订：保留旧产物，将受影响的步骤标记为需要更新，只重新运行这些步骤和依赖它们的下游。不因用户改一句报告标题就重复搜索所有信息。多个修改同时到达时用版本检查串行接受修订，避免并发覆盖。

代码职责建议：

- 现有 `agent/contracts.py`：扩展类型化任务、结果、模型需求和路由决策。
- 现有 `agent/registry.py`：保存角色说明、默认任务偏好和工具权限。
- 模型目录/网关旁新增薄路由模块：纯候选选择与决策记录；真正重试和 provider 参数映射复用网关。
- 从现有协调器逐步抽出子会话、调度、验收服务：保持现有入口和旧任务读取兼容，不一次重写整个 `subagents.py`。
- 复用 jobs/outbox 和管理 API：新增必要字段、版本与事件，React 只消费真实状态。

长任务在宿主确认已持久化后，给群里一个简短已接单回复；后台执行进程接手。任务沙盒在产物被复制到持久存储并完成必要投递后回收，失败任务保留限时诊断资料。不能先销毁沙盒再试图发送里面的 PDF。

执行成功、验收成功和投递成功独立保存。用户要求发文件时，只有必需产物通过验收且发送得到确认，任务才能报告完整完成；回执不明进入待核对，而不是当作模型失败重新生成和重发。

## 5. 一条实际工作流

### 5.1 调研并制作报告

用户：“帮我比较几款固态硬盘，整理成中文 PDF 发我。”

```text
主控 Terra：确定比较范围和交付标准
  |
  +-- 搜索 A / Luna：官方参数 --+
  |                            +-- 分析 / Terra：有出处的比较 --+
  +-- 搜索 B / Luna：当前价格 --+                               |
                                                               v
                                                      文件 / Terra：生成 PDF
                                                               |
                                                      宿主：检查内容与字体
                                                               |
                                                       合格 -> 投递并记录回执
                                                       不合格 -> 局部修复
```

如果价格查询失败，但参数齐全，主控可交付“参数比较版，缺实时价格”，不能编造价格。如果用户接着说“去掉第三款”，继续相关子会话、更新产物版本，不重复查询所有来源。

若来源互相冲突，分析 Agent 可提出升级到 Sol 的需求，由宿主在权限内批准并继续同一个分析子任务；不让两个搜索 Agent 也一起升级重跑。上述模型均以已经完成渠道验证为前提。

### 5.2 开发谷粒商城

“精心写个谷粒商城”的目标路径应是项目工作流，而不是等待用户换一句带关键词的表达。主控先明确本轮功能范围、接口、启动方式和验收标准；若是多阶段完整项目，把未实现部分列入后续目标，不冒充一轮即可交付全部。

```text
主控：识别项目开发，提出范围和可执行任务合同
   |
设计步骤：模块边界、接口、数据结构、目录和验收规则
   |
   +-- coder/frontend：自己的会话和前端工作区 --+
   |                                           |
   +-- coder/backend：自己的会话和后端工作区 ---+--> 集成步骤
   |                                           |       |
   +-- coder/tests：按接口编写测试用例 ----------+       v
                                              构建、启动、接口与页面检查
                                                       |
                                              document：最终使用说明
                                                       |
                                              产物验收、打包、投递
```

测试设计可以和前后端实现并行，真正执行集成测试要等对应实现可用。说明文档可提前准备框架，但最终启动步骤必须用实际运行结果更新。若某项工作依赖未确定的接口，就先等接口，不为制造并行动画而提前启动。

前端、后端和测试均可复用 coder 的角色模板，但实例身份、工作目录、模型、上下文和结果分别保存。普通实现优先考虑已验证的 Terra；难模块可选已获授权的 Sol；小范围后续代码修改可选 Spark。角色数量由工作量决定，不强制每个商城请求都启动相同人数。

每个 worker 拿到相同版本的接口合同，但只收到自己需要的详细资料。它们提交版本化产物或改动，由集成步骤合并；不能争用同一个可写目录。接口变更形成新版本，通知受影响步骤，由主控决定继续、暂停或局部重做。

可见进度应类似：“接口已确定，前端和后端开始并行”“后端通过接口检查，前端正在联调”“构建失败在依赖配置，代码 Agent 正在修复”。主控在真实结果到达后发送，不提前编造成功状态。

最后交付源码、启动说明和必要验证记录。公开部署商城、接入真实支付或使用外部付费服务仍需单独授权，不能把“写商城”扩展成这些操作的自动许可。

## 6. 实施顺序

| 顺序 | 改什么 | 验收重点 |
| --- | --- | --- |
| 0 | 固化谷粒商城路由复现案例；校正模型目录并验证必要渠道能力 | 记录现有漏判；不把纯文本模型派去识图，不把未验证项当作可用 |
| 1 | 主控语义执行决定、任务/结果合同、执行入口约束和验收投递状态 | “写商城”进入任务，“解释商城”直接答；无效结果不能成功，完成与送达分开 |
| 2 | 子会话消息持久化、完整结果引用、受控继续执行 | 追加要求可接着做；上游结果不再截断；不串群、不泄露个人记忆 |
| 3 | 统一角色模型、能力、推理和执行策略 | 配置实际生效；期望和实际模型可解释 |
| 4 | 后台任务接管、租约、版本检查与投递对账 | 重启后安全续跑；不盲目重放副作用 |
| 5 | 有限动态调整、资源公平调度、并行工作区 | 快分支不等慢分支；失败只修局部；文件不相互覆盖 |
| 6 | 完善真实事件、任务图与端到端评价 | 图和实际并行一致；能说明哪里失败及交付了什么 |

事件与审计字段随前面各步同步补，最后一步主要完成展示和整体测量，不是最后才做可观测性。

每一步先本地完成，再经用户确认上线；自动选型先以“只记录建议、不改变实际模型”的观察方式检查决策，再对管理员任务开放，最后扩展到其他群友。新增表和字段通过 Alembic 做兼容迁移；旧任务继续旧执行路径或明确等待迁移，不让切换版本悄悄重跑历史副作用。

上线保留开关，可关闭新路由或自动接管，但不会清空已有子会话、任务证据和投递记录。未来部署仍须遵守共享 h610 的 fetch、检查远端差异和用户确认要求，本设计不授予自动 rebuild 权限。

少而关键的验收案例即可先覆盖：并行检索、追加修改中文 PDF、上游部分失败、重启接管、投递回执不明、跨群越权拒绝、并行写文件冲突。比较成功交付率、总耗时、Token、重复工作量和人工介入次数，不用“启动了多少 Agent”衡量进步。

分工入口额外保留少量真实成对用例：“精心写个谷粒商城”“谷粒商城是什么”“前后端分工并行实现，最后测试打包”“只给我一个排序函数”“继续上一个项目，加购物车”。规则和合同校验用离线测试；语义选择再用固定小样本模型验证，不反复全量消耗额度，也不声称离线规则测试证明了模型判断准确率。

## 7. 暂时不做

- 不更换整个机器人框架，不同时叠加多个编排 SDK。
- 不为了像大公司而先加一套集群和消息中间件。
- 不新增很多名称不同、职责却重复的常驻 Agent。
- 不让每个小任务都经过额外规划、讨论、评审三轮模型调用。
- 不把独立上下文做成全员互读的共享聊天记录。
- 不重写群聊主上下文或改数据库主备拓扑。

第一优先级是把当前已经能工作的多 Agent 变成“知道交付标准、信息交接完整、失败后可继续”的系统。
